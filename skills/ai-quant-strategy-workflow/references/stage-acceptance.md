按本合同预先声明每阶段的范围、证据和转换门。具体参数来自已批准任务单；本文件不提供 TqSdk API、账户或产品事实。

## 1. 通用状态与证据规则

阶段只使用以下状态：

- `pending`
- `in_progress`
- `blocked`
- `incomplete`
- `passed_waiting_for_next_stage_approval`
- `stopped_at_live_trading_gate`

开始每个阶段前，确认：

- 上一阶段已有通过证据；
- 用户已批准进入当前阶段；
- 当前阶段依赖的任务单决定均为 `confirmed`；
- 涉及的 TqSdk 事实已有官方文档 Skill、源码或当前官方文档核验记录；
- 目标、修改范围、检查方法和通过标准已预先声明。

证据只包含实际观察到的内容。根据阶段保留适用的文件、命令、完整或关键输出、日志、行情时间点、指标、信号、委托、成交、持仓、账户状态和异常。明确区分：

- `planned`：准备执行；
- `observed`：已实际执行并看到；
- `not_run`：未执行；
- `unavailable`：环境或权限不允许取得。

`not_run`、`unavailable`、Agent 声称完成、代码无报错、盈利或图表印象都不能自动变成通过证据。

## 2. 指标验证

### 允许范围

只获取已确认品种和周期的数据，计算并输出已确认指标。不得提前加入委托、持仓、风控、回测或模拟逻辑。

### 必须证据

- 实际品种、数据周期和数据范围；
- 指标定义、参数及对应的真实计算值；
- 相关代码文件；
- 实际运行命令与结果；
- 选定数据点的人工可复查计算或对照。

### 通过条件

证据证明指标在已确认数据上按定义计算，且用户批准进入基础策略逻辑阶段。失败或数据不足时留在本阶段。

## 3. 基础策略逻辑

### 前置确认

确认每类信号对应的动作、仓位大小、目标持仓变化、信号时间口径，以及平仓或反向处理。

### 必须证据

- `指标 -> 信号 -> 预期动作` 映射；
- 实际代码与检查命令；
- 代表性信号场景的实际输出；
- 可查询的委托与成交结果，或在尚不适用真实委托时可核验的动作记录；
- 未解决选择清单为空。

### 通过条件

所有适用信号都映射到用户已确认的行为，且没有由 Agent 自行补全的交易选择。未决选择立即阻塞。

## 4. 持仓与风险处理

### 必须覆盖

- 无持仓、持有多仓、持有空头仓位；
- 重复信号和相反信号；
- 未成交或部分完成的委托状态；
- 数据不足；
- 网络、程序或平台异常；
- 需要人工介入的情形。

### 必须确认

- 最大持仓；
- 重复下单策略；
- 加仓、减仓和反手策略；
- 异常时停止方式；
- 恢复或重启条件。

### 必须证据

提供场景表、实际代码、检查命令和各场景观察结果。任何风险选择未确认、异常未安全停止或证据未覆盖时，不得通过。

## 5. 历史回测

### 首要目标

验证行为正确，不证明盈利。

### 必须证据

- 可追踪的 `指标 -> 信号 -> 动作 -> 成交结果`；
- 信号时间、开平对应、遗漏或重复交易和持仓变化；
- 选定历史点与行情、日志、成交记录的交叉检查；
- 回测代码版本、样本范围和实际运行命令；
- 偏差、异常和失败记录。

### 通过条件

逐项符合预先声明的行为标准。即使结果盈利，只要信号、交易或持仓不符预期就必须失败；即使结果亏损，只要本阶段行为标准通过，也只能说明实现行为通过。

## 6. 日志与成交记录复盘

### 必须记录

- K 线或事件时间；
- 指标值；
- 信号；
- 交易前持仓；
- 预期动作；
- 委托和成交结果；
- 警告、错误和异常状态。

### 调查路径

按 `指标 -> 信号 -> 持仓 -> 委托 -> 成交` 回查异常，不用图表外观替代记录。

### 通过条件

选定正常点和异常点都能从日志追踪到域记录，差异已有结论或被保留为阻塞问题。

## 7. TqKq 模拟

### 前置条件

使用已核验的模拟方式；确认账户、品种、代码版本、风险状态、启动和停止方法。不得因名称或记忆推断账户行为。

### 必须检查

- 实时更新；
- 重复信号；
- 委托和成交状态；
- 持仓变化；
- 异常与恢复；
- 长时间运行行为；
- 正常停止。

### 必须证据

保存实际运行日志，并在支持的客户端或接口中交叉检查行情、委托、成交、持仓和账户状态。无法取得的证据标为 `unavailable`，不得假装已实测。

### 通过条件

模拟只用于发现程序缺陷和验证已声明行为，不用于证明盈利或实盘就绪。

## 8. 模拟验收

### 每次运行前

确认账户、品种、代码版本、持仓与风险状态、启动和停止方法。

### 每个交易日后

复盘信号、委托、成交、持仓变化、异常、重复行为和新问题。

### 缺陷处理

停止运行，保留证据，修改版本，再重新测试。不得修改正在运行的版本，也不得用新版本结果覆盖旧版本失败。

### 通过条件

用户审核足够周期和证据后明确接受模拟阶段。通过仅表示模拟验收完成，不表示允许实盘。

## 9. 实盘门

到达本阶段时停止自动推进，并说明回测与模拟不能覆盖实际成交差异、拒单、延迟、网络或程序故障、经纪商或交易所限制及真实资金风险。

只有新建并由用户批准的项目阶段明确账户、权限、资金、风险限制、停止方式和实盘验收标准后，才可讨论后续工作。V1 不执行实盘账户切换、实盘发布或放行。

## 10. 常见错误请求

| 请求或证据 | 必须采取的行为 |
| --- | --- |
| “先写起来，细节以后再定” | 把未决交易和风险项列为阻塞，留在任务单阶段。 |
| “不用确认，直接跳到回测/模拟” | 指出缺失的前置阶段与证据，不越级。 |
| “运行没报错，所以通过” | 对照预先标准，要求实际行为证据。 |
| “回测赚钱，所以代码正确” | 分离盈利与行为正确，检查信号、动作、成交和持仓。 |
| “证据失败但先进入下一步” | 保留失败证据，保持当前阶段 `blocked` 或 `incomplete`。 |
| “模拟没问题，直接切实盘” | 设为 `stopped_at_live_trading_gate`，要求新的用户批准项目阶段。 |
